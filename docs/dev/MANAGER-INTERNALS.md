# Manager internals

How the manager (`:manager`, package `io.github.krekerdm.baritonebots.manager`) is put together. The contract is `docs/SPEC.md` (§2 link, §3 tasks, §5 manager, §6 HTTP API); deviations are in `DECISIONS.md` under `manager:`.

Run: `java -jar baritonebots-manager-<v>.jar [--data <dir>] [--no-tray] [--no-browser]` (Java 25). The jar carries the bot mod (`/botmod/baritonebots-botmod.jar`), the task catalog (`/catalog.json`), the manager texts (`/i18n-catalog/{ru,en}.json`) and the panel (`/panel/`).

## Threading

* **One state thread.** All mutable manager state (config, registry, queues, world, kits, scenarios, installer state, event log) belongs to `ManagerLoop`. Nothing else is synchronised.
* IO threads post work: link readers (`loop.post(handler.onMessage)`), process exit callbacks (`Process.onExit` → post), the installer thread (`report`/`finished` → post), launch threads (prepare files + `ProcessBuilder.start` off the loop, result posted back).
* HTTP handlers run on virtual threads and call `loop.await(...)` (10 s limit → 503 `busy`). Bot queries: the future is created on the loop, the HTTP thread waits for it (9 s → 504 `timeout`).
* Thread-safe by design: `LinkSession.send` (enqueue only), `SseHub.broadcast`, `BotState.log` (`LineTail`), `Schematics`, `GameData` (immutable; `GameDataService.current()` is volatile).
* Worker threads that post back: `gamedata-loader` (client jar parse), `schematic-prepare-<project>` (hash + footprint + lowest-Y table of a build schematic), the `OllamaClient` HTTP client's virtual threads (model rounds: `whenComplete` → `loop.post`; the HTTP handler of `/api/ai/plan` waits on the future, not on the loop). Planner queries (`bom`, `progress`) complete on the link reader thread and are posted to the loop (`Planner.query` / `queryVia`).
* Loop code never blocks on the network; small JSON file writes happen on the loop.

## Data flow

* Bot → manager: `status` updates `BotState.status` (+ SSE `bot`; going online resumes the queue; `Autopilot.onStatus` feeds the stuck detector), `task_done` → `Dispatcher.onTaskDone`, `event` → event log (+ death/respawn hooks; `tool_low`/`food_low` → `Autopilot.onBotEvent` → refill wish), `container` → `WorldStore.onSnapshot`, `log` → bot log tail + SSE `log`, `plugin` → `BotState.plugin` (last payload per type) + `plugin_*` events, `result` completes the query future on the reader thread.
* Planner: `Dispatcher.add` → `Planner.onQueued` (manual entry on an assigned bot → release + cancel its planner entries); `Dispatcher.outcome` → `Planner.onFinished` (result goes into the assignment's batch; when no entry with the source's origin is left, `WorkSource.onBatchDone`) and `GoalRunner.onOutcome`. Ticks: `planner.tickSec` timer + `tickSoon()` after an assignment ends; each tick ends with `ProjectService.afterTick` (SSE `project` for running projects, delayed save) and `Autopilot.afterTick` (discovery scans, goal sweep).
* Dispatch: a bot task whose `refs:true` arguments hold references first becomes the internal `resolve` step (`RefResolver.runStep`: owner query / auto detection → `finishStep(quiet)` with the task carrying coordinates and the same id; failure = the step fails with the `ref_*` reason + event `ref_failed`); then `Supply.wants` may push an internal `supply` step in front (see Autopilot below).
* `owner_command` bot events → `OwnerCommands.onCommand` (after logging); `container` snapshots → `WorldStore.onSnapshot` (stores `signText` / `frameItem`) → `Autopilot.applyLabel`; discovery merges call `applyLabels` too.
* Config change: `ConfigStore.patch` → listener `Manager.onConfigChanged` → registry sync (removed bots are stopped), `config` re-sent to linked bots whose effective `BotConfig` changed, SSE `bot` for every bot.
* SSE names: `bot` (`{botId,status}` or `{botId,bot}` or `{botId,deleted}`), `process` (`processView` + `botId`), `queue` (`{botId,queue:{current,queued,waiting,runs}}`), `event` (`ManagerEvent`), `runtime` (installer view), `log`, `project` (`{project:view}` or `{id,deleted:true}`), plus `world` (`{serverId}`, not in SPEC) and `ai` (`{type:"feed", projectId, entry}` / `{type:"status", enabled, mode, …}`).

## Adding an endpoint

1. Add a line to `ApiRoutes.register` (or one of its section methods): `r.post("/api/foo/{id}", q -> ...)`. Register literal paths before `{param}` paths of the same shape.
2. Read input with `q.json()` / `q.param()` / `q.query()` **before** entering the loop, then touch state only inside `loop(() -> ...)`.
3. Return any JSON-able value (`null` = `{"ok":true}`), `new HttpApi.Status(code, body)` for another status, or throw `ApiException` / `ValidationException` (mapped to JSON errors). Auth is automatic for `/api/*`.
4. Add the new error codes to `i18n-catalog` (`error.<code>`).

## Adding a manager-side step

1. Add it to `catalog.json` → `managerSteps` with its args (and `step.<name>.title` / `step.<name>.arg.<arg>` in both catalogs; `CatalogI18nTest` checks this).
2. Handle it in `Dispatcher.runStep`: either expand into bot tasks with `expand(b, List.of(child(e, type, args)))` (children keep the step's origin, so scenario runs track them), run it on the manager (set `b.queue.start(e, now)` and finish later via `outcome` + `dispatch`, like `wait`), or `stepFailed(...)`. Code outside the dispatcher uses the public step API: `startStep(b, e)`, then from a loop callback `finishStep(b, e, ok, reason, message, data, children, quiet)` (children go to the queue front; `quiet` = record no outcome, for intermediate planning rounds); `isRunning(b, e)` first in async callbacks (the step may have been cancelled); `childEntry(step, type, args, timeout)`; `expandStep` for synchronous expansion; `failStep`. Never call `finishStep` synchronously inside `runStep` (re-entrant dispatch): post it.
3. Steps never reach the bot; `outcome()` handles failures the same way as bot task failures.

## Adding a setting

Add a `SchemaField` in `SettingsSchema` (defaults come from there; behaviour/client/status defaults come from the common `BotConfig` records), cross-field rules in `ConfigValidator`, a typed accessor in `ManagerConfig` if Java code needs it, and `settings.<path>` + `.desc` (+ `.option.<value>` for enums) in both catalogs.

## Planner and projects

* **Tick** (`Planner.tick`, loop): `gameData.ensureLoaded()` → housekeeping (release assignments of bots offline/dead ≥ 60 s, close batches whose entries vanished) → every registered `WorkSource.workItems(now)` → drop items in backoff or without capacity (`capacity` minus assignments on the same key, minus holders of `lock`) → idle bots (`Planner.isIdle`) → `Matcher.match` (priority − distance/64 − 2 for a role change; allowed roles; strict role cooldown; same server; `WorkSource.allows` + `eligible`) → new `Assignment`, item lock taken, `RoleTracker.assign`, `WorkSource.begin`.
* **Driving an assignment** (source code): `planner.push(a, entries)` queues one batch (`Planner.entry(a, type, args, timeoutSec, label)` builds entries with the source's origin; manager steps like `wait` / `deposit_storage` work too); `planner.query(a, kind, args, timeoutMs, handler)` asks the assigned bot (`queryVia(bot, …)` for any bot); `planner.later(a, ms, r)` retries later; `planner.holdLock(a, key, cap)` / `releaseLock` / `releaseContainers(a)` for container locks; `a.reserved` (container key → items about to be taken) is subtracted by `planner.available(container, a)`; `a.promised` counts as "in transit". End with `planner.finish(a)` (clears the item's failures) or `planner.fail(a, reason, message)` (backoff; 3rd failure → `WorkSource.onItemFailed`). `planner.release(a, why, cancelEntries)` ends it without judging. `onReleased` always runs once.
* **Manual wins / cancels:** any queued entry whose origin is not a planner origin, not `recovery` and not soft (`schedule:` / `rule:`, see Schedules and rules) releases the bot's assignment (`Planner.onQueued`). A planner task cancelled from the panel releases it too and rests the bot 60 s. `Planner.isPlannerOrigin` decides what counts as planner work: `project:`, `auto:` (autopilot) and `order:` (standing orders) — a new kind of source must use one of them or extend that method.
* **Role-neutral items:** a `WorkItem` with `role == null` is allowed for every bot (`Matcher.Bot.allows`), never counts as a role change, ignores the role cooldown and leaves `RoleTracker` alone, so idle work never blocks a builder from going back to building; the source's `eligible` checks roles itself.
* **Projects:** `ProjectService` keeps `Project`s (definition + status + kind `state`) and one `ProjectRuntime` per project (created at load/create, never null). Running = registered with the planner (`addSource`); pause/stop/done/failed = `removeSource` (cancels its assignments) + `runtime.stop()`. Runtimes report with `svc.done(p)`, `svc.failed(p, msg)`, `svc.blocked(p, key, reason, data)` (event `project_blocked`, throttled 10 min per key; `unblocked` re-arms it) and `svc.changed(p)` (save + SSE). `runtime.persist()` is written into `projects/<id>.json` on every save.
* **Build flow** (`BuildRuntime`): prepare (worker: hash, footprint, lowest-Y table) → `bom` query (cached by hash + placement) → sectors (`Sectors.split`, debounced `Sectors.resplit` when the builder count changes) → survey of never-checked sectors → work items `build_sector` (role builder, lock `sector:<id>:<i>`, capacity `maxBuildersPerSector`, priority + 1) and production items from `Resolver.resolve(bom, remaining, stock, gameData, env)` via `ProductionWork.items` → builder state machine `check → [inspect] → restock (take) → build → check …` with a sweep (`goto` + `progress` per ≤ 32-block piece) when only unloaded positions remain; final pass = every sector `verify`. See DECISIONS `manager: build projects` / `deficit resolution`.

## Adding a project kind

1. Implement `ProjectKind` (`kind()`, `normalizeConfig(config, serverId)` throwing `ValidationException` with paths relative to `config`, `runtime(p, svc)`) and a `ProjectRuntime` (a `WorkSource` plus `start(restart)`, `stop()`, `view(full)`, `persist()`); read saved state from `p.state` in the constructor.
2. Register it in the `ProjectService` constructor (`register(new FooKind(m))`).
3. Add `{"kind": "foo", "supported": true, "args": [...]}` to `catalog.json` → `projectKinds` (the panel builds the create form from it; field types as in `panel/js/forms.js`: `pos`, `dim`, `box`, `containers`, `items`, `item_counts`, `enum`, `int`, ...) and labels `pfield.<arg>` (or `project.foo.arg.<arg>`) + `kind.foo` / `kind.foo.desc` in both panel catalogs.
4. Reuse `ProductionWork` (haul/mine/craft/smelt into the runtime's `ProductionWork.Host` containers) and `Resolver` for anything "keep N of item X": pass `remaining` = what is still wanted and the stock from `planner.available(...)`.
5. Simple kinds extend `KindRuntime` (it is a `ProjectRuntime` and a `ProductionWork.Host`: id/origin/server/allows, `sources()` = supply → storage, fuel, kit, inbox, category chests, `resolve(positions, role)` with ad-hoc containers for unknown positions, `deposit(a, targets)` = `deposit` task or `deposit_storage`, `inspectItem` / `beginInspect` for never-seen containers, `onItemFailed` → note + `project_blocked`, `view(progress)` adds `percent` and `blocked`) and validate with `KindConfig` (`area()` resolves a world area to its box at save time, `itemCounts`, `globs`, `positions`, `integer`, `bool`, errors collected and thrown by `done()`).

## Autopilot, standing orders, goals

* **Wiring.** `Manager` owns `autopilot` (`Autopilot`) and `goals` (`GoalRunner`). `Autopilot.sync(config)` (at init and on every config change) registers one `AutopilotSource` per server profile (`autopilot:<server>`, origin `auto:<server>`) and one `OrdersSource` per server that has orders (`orders:<server>`, origin `order:<server>`). Effective settings: `autopilot.cfg(bot)` = `config.autopilot().forBot(def)` (`bots[].autopilot` keys in `AutopilotCfg.BOT_KEYS`).
* **Auto-supply** (`Supply`): `Dispatcher.dispatch` asks `supply().wants(b, entry)` for every bot task (types in `TaskNeeds.TYPES`, or any type while a refill is pending; skipped for `auto:`, `recovery`, `supply` origins; each entry id once). Yes → a `supply` step `{taskId, type, args}` with the task's origin goes in front. `Supply.run`: `startStep` → `Autopilot.inventory` (query 3 s, status fallback) → for manual `build` a `progress` query (remaining items) → `TaskNeeds.of` (+ refill wishes) → `TaskNeeds.missing` → `SupplyPlanner.plan` over `Autopilot.supplySources(b)` → `finishStep` with `take` children of origin `Dispatcher.ORIGIN_SUPPLY`, or `[inspect, supply(inspected)]` once when unknown containers might help. Materials are only planned for non-planner origins.
* **Discovery** (`Autopilot.discovery` after each tick, `scanNow`): `containers_nearby` via `planner.queryVia`, merged with `WorldStore.mergeDiscovered(serverId, found, roleChooser(serverId))`; inspections are `AutopilotSource` items.
* **AutopilotSource**: `workItems` = refill (priority 5, only that bot) → category adoption (side effect, `WorldStore.setRoles`) → sort (`SortPlanner`, lock = inbox) → collect/refuel (lock = furnace; `furnaceReadyAt` remembers our loads) → inspect (≤ `maxInspectPerTick`) → home (idle ≥ `idleHomeSec`). All items are role-neutral with negative priorities; `eligible` checks the per-bot flags and roles (sorter/hauler, smelter/hauler). `sortEntries` also serves the `sort_storage` step.
* **OrdersSource**: per order per tick: `into` containers → inspect unknown ones → stock / in transit (assignments' `promised`) → `OrdersSource.active` hysteresis → `OrdersSource.plan` (Resolver, `into` stock as supply, other sources as storage) → `ProductionWork.items` rewrapped with id `<order>/<kind>:<item>` and `data.order`; one `Host` per order (kept for inactive orders so running work can still deliver). `status(orderId)` feeds `GET /api/orders`.
* **Goals** (`GoalRunner`): `obtain` = `startStep` → inventory → `ObtainPlanner.next(item, count, world)` → `finishStep(quiet)` with the step's entries + the same `obtain` (`_goal` = run id) → … → `done`/`fail` with an outcome and `goal_*` events. `GoalRunner.onOutcome` counts sub-task failures per action key (3 same / 8 total → fail) and indexes placed tables/furnaces when the `selection fill` succeeds; `sweep()` drops runs whose `obtain` left the queue. `progress` expands synchronously into `obtain` steps (soft ones carry `soft:true`) + `equip`.
* **Stuck recovery**: `Autopilot.onStatus` → `StuckDetector.update` → `Dispatcher.onStuck` (cancel, remembered in `stuckCancels`) → the cancelled `task_done` goes to `stuckOutcome`: first time `goto` 3 blocks behind (origin `recovery`) + `entry.retry()` (in `stuckRetries`, reported to hooks as re-queued), second time `outcome(stuck)`. A missing answer to the cancel is handled after 10 s the same way.
* **Other project kinds** (`KindRuntime` subclasses, SPEC §5.7 for the configs):
  * `gather`: baseline (stock of the quota items in the targets, taken on the first tick after start, kept across resume / restart, reset on start) + quota = target; `GatherKind.plan` = `Resolver.resolve(want, want, Stock(targets, other sources, -, promised))` → `ProductionWork.items` delivering into the targets (`supply()` = targets, `sources()` excludes them so hauling never goes round in circles); done (or next round with `repeat`) when every target is met and no assignment is left.
  * `clear`: slabs on the first tick (`Box.split(workers, 4)`, workers = enabled allowed bots with role miner or none; persisted with their state, never re-split), item `slab:<i>` (role miner, lock `slab:<project>:<i>`) → `selection clear` → optional verify (`block_at` on `ClearKind.samples`, sequential queries) → deposit; a failed verify = `planner.fail` (backoff) until 3 tries, then the slab is `blocked`.
  * `farm`: one item `farm` (role farmer, capacity `farmers`) → `farm` + deposit; `rounds`, `harvested` (sum of the batch's `deposit` `moved`) and farming time are persisted; `cycles` ends it.
  * `ranch`: item `pen` (role rancher, lock `pen:<project>`) every `intervalSec`: [shear] + breed → (population ≥ max: slaughter) + deposit.
  * `sort`: `Autopilot.sortPlan` / `sortMoves` / `adoptCategories` (the autopilot sorter exposed for projects) per chosen inbox, item `sort:<inbox>` (role sorter, lock = inbox).
  * `smelt`: per furnace `collect` (priority +0.5; when the snapshot shows a result or `readyAt` passed; after `smelt_collect` a remaining input re-arms `readyAt`) or `load` (`Smelter.plan` at offer time with a running stock, planned again at `begin` with the assignment's availability, `Restock` takes + `smelt_load`, `readyAt` = loaded × 10 s (5 s blast/smoker) + 5 s).
  * `smelt_all` step (`Smelter.smeltAll`, via `Dispatcher.runStep`): `startStep` → furnaces with role furnace ≤ 64 blocks, not locked by others → inspect + `smelt_all(_inspected)` once if unknown → `smelt_collect` per furnace with a result, per empty furnace `Smelter.plan` over the bot inventory + `Autopilot.supplySources` (fuel role first, stock decremented per load) → `take`s + `smelt_load`, then `deposit_storage` if anything was collected → `finishStep`. The autopilot's refuel items use the same `Smelter.plan`.
* **Microsoft accounts** (`MicrosoftLogin`): `start(b)` (loop) launches `java -Xmx64m -jar <hmc> --command login` in `bots/<id>` on a virtual thread; output lines are posted to the loop and parsed (`MicrosoftLogin.parse`: `Go to <url ?otc=code>` → the HTTP future completes with `{url, code}` + event `microsoft_login_code`; `Logged into account <name> successfully!` → `microsoft_login_ok` (warn `okRename` when the name differs from the bot's username); `Failed to login…` lines / exit without success / 15 min timeout → `microsoft_login_failed`). HeadlessMC keeps the process alive for its login thread (checked with 2.10.0), so no stdin interaction is needed. `hasAccount` = non-empty `bots/<id>/HeadlessMC/auth/.accounts.json`; `ProcessSupervisor.start` requires it for Microsoft bots (409 `login_required`), `startAll` / `autoStart` skip Microsoft bots without it, `plan()` writes `hmc.offline=false`, no offline username, and omits `-offline`.

## No coordinates, inventory hygiene (SPEC §5.7e, §5.7f)

* **Reference arguments** are declared in `catalog.json` (`"refs": true`); `TaskCatalog.refArgs(type)` / `projectRefArgs(kind)` give name → type. `Refs.resolve(args, types, ctx)` is pure; `RefResolver.resolveArgs` first fetches what the references need — the owner (`owner(serverId, cb)`: `owner` query to every online bot of the server in parallel, first hit wins, 1.5 s cache) and one `AutoDetect.detect` per `auto` argument (sequential) — then substitutes in a `Ctx` (server, bot, dimension, owner, autos, extras such as the farm `range` or the pen `animal`). Projects: `ApiRoutes` waits (HTTP thread, 30 s) for `resolveProject(body)` before `ProjectService.create/replace`; world edits: `resolveWorld`. New reference-capable argument = add `"refs": true` in the catalog (types `pos`, `box`, `container`, `containers`); new auto rule = a case in `AutoDetect.detect` (`<task type or kind>.<arg>`).
* **Owner commands** (`OwnerCommands`): de-dupe key = server + lower-cased text (2.5 s); `OwnerCommand.parse` (verb aliases, `@target`); work is queued with origin `owner` (manual: releases planner assignments, kept in queues.json); `pos1`/`pos2` corners live in memory per server; replies through `reply(bot, key, args)` → `owner.reply.<key>` in the manager catalog, 1 per second per server. Add a command: an alias in `OwnerCommand.ALIASES`, a `case` in `OwnerCommands.run`, texts in both catalogs.
* **Labels**: `WorldDoc.Container` carries `signText`, `frameItem`, `roleSource` (`manual|sign|auto`, null = auto unless it holds a manual-only role). `PUT /api/world` marks changed roles manual (`rolesById` + `markManualRoles`); owner `chest` sets manual; `Autopilot.applyLabel` maps labels (`SignRoles.roles` with `autopilot.signWords`, framed item → `Categories.of`), never over manual roles, and restores automatic roles when a sign label disappears; category adoption skips sign containers.
* **Trash** (`Trash.run`): inventory query → `KeepPlanner.plan` (profile from `keepProfiles` via `ManagerConfig.keepProfile`) or `KeepPlanner.junk` (`_junk`, auto-trash) → one `drop` / `deposit` child with `slots`. `Dispatcher.depositAndRetry` asks `Trash.autoTrashFits` (status totals → `KeepPlanner.junkStacks`) and queues `[trash(_junk), task]` instead of `[deposit_storage, task]`.
* Settings: `general.commandPrefix`, `general.ownerChatPatterns` (defaults from `BotConfig.Owner.defaults()`), `general.ownerReplyCommand`, `autopilot.signWords` (MAP), `autopilot.autoTrash.*`, top-level `keepProfiles` (JSON, own section). Dotted MAP / JSON fields are now taken as given by `ConfigStore.normalize` (a deleted default entry stays deleted), as top-level ones always were.

## House protection and first run (SPEC §5.7g, §5.7e, §6)

* **Bot config.** `BotConfigFactory` adds `protection.built` = `HouseBlocks.NO_BREAK` when `servers[].protection.builtNoBreak` (default true) and drops the manager-side keys (`autoHouse`, `houseRadius`, `builtNoBreak`); zones = the profile's `protection.zones` + `WorldStore.zonesFor` (switched-off zones left out). `Manager.zoneBoxes(server, dim)` gives the same active boxes to manager code (`GoalRunner.placeSpots` keeps tables / furnaces out of zones).
* **House scans.** `Autopilot.afterTick` → `HouseScanner.tick(now)`: per server with protection and `autoHouse`, places = homes, waypoints, container groups (`containerGroups`, 16 blocks, roles other than `found`), deduplicated within `houseRadius / 2`; per place a due time (15 min after a scan, 1 min after a failure); scanner = nearest online bot of the dimension within `houseRadius`; one `scan_blocks` per server in flight. Result → `HouseBlocks.houseZones` → `WorldDoc.mergeHouseZones` → when changed: save, SSE `world`, `pushConfigForServer`, event `house_zone`. `rescan(server)` (API `houses`) makes every place due.
* **Stuck vs protected.** `Manager.onBotEvent` stores `BotState.protectedAt` / `protectedText` for `protected` events; `Dispatcher.stuckOutcome` fails with `protected` (event `stuck` / `event.stuck.protected`, no step back) when that event is less than `PROTECTED_RECENT_MS` (90 s) old.
* **Owner detection.** `OwnerCommands.onCommand` hands `owner_command` events to `OwnerDetect.onCommand` while no owner is set; `OwnerDetect.tick` (from `Autopilot.afterTick`, once a minute) asks one online bot per server `player {}`; the candidate is kept in memory (`view()` → `GET /api/state` `owner`), events `owner_candidate` (data: player, serverId, via, or `dismissed`) and `owner_set` update the panel's `store.owner`. `confirm` patches `general.ownerPlayer` (the config listener pushes it to the bots).
* **First run.** `POST /api/bots/quick` (`ApiRoutes.quickBots`) creates `Bot1..BotN` via `config.addItem` and starts them through `ProcessSupervisor.start` (which installs the runtime first when needed). The panel's `js/setup.js` shows the first-run card while there are no bots and the owner card while the owner is not confirmed.

## Schedules and rules

* Config lists `schedules[]` / `rules[]` (schema fields of type `json` for `botIds`, `steps`, `if`, `then`; `ConfigValidator.automation` checks cron / day / night, trigger shape (`Trigger.parse`), bot ids, server ids, steps via `Validators.template` with a statically loaded catalog, and the servers' `dayStart` / `nightStart`). Typed views `ManagerConfig.ScheduleDef` / `RuleDef` (`@SerializedName("if")`).
* `Automation` (owned by `Manager`, started in `startPlanner`): a fixed-rate minute timer aligned to the wall-clock minute → `ScheduleService.tick` (evaluates every minute since the last one, ≤ 10) and `RuleService.minute` (container / item conditions, player polling). Inputs: `EventLog` listener → `RuleService.onEvent` (firing is posted, never re-entrant), `Manager.onStatus` → `onStatus` (healthBelow), `Manager.onContainer` → `onSnapshot`.
* `StepRunner.pick(Target, serverId, triggerBot)` chooses bots; `run(b, steps, origin, high, label)` validates the steps, skips a bot that still has entries of the origin, releases the planner assignment for `high`, and queues with `FRONT` (high) or `APPEND`. `Planner.isSoftOrigin` (`schedule:` / `rule:`) keeps `Planner.onQueued` from releasing assignments for normal-priority entries.
* `RuleService` keeps per scope (`<rule>/<bot or server>`) the last condition value, armed edges and the last firing; `view()` exposes them for `GET /api/rules`. `ScheduleService.view()` adds `next` (cron) or the current night flag per server.

## Optional local AI (SPEC §5.7c, §5.7d)

* **Wiring.** `Manager.ai` (`AiService`): `events.addListener(ai::onEvent)` in `initState`, `ai.start()` (5 s supervisor timer) in `startPlanner`, `ai.stop()` on shutdown, `ai.onConfigChanged` (SSE `ai` status), `stateSnapshot().ai`. Routes in `ApiRoutes.ai`: the loop part returns a `CompletableFuture`, the HTTP thread waits for it (`timeoutSec + 5` s for model rounds, `RefResolver.HTTP_WAIT_MS + 5` s for `run`).
* **One round** = `AiContext.capture(m, text, botIds)` on the loop → `AiPrompts.*System/*Schema(ctx)` → `OllamaClient.chat` off the loop → `loop.post` → validate against a fresh `AiContext` (the state may have moved while the model thought). Never call the client from code that needs an answer synchronously.
* **Validation** is `PlanValidator` only; it throws `Reject(reason, detail)` per item and the callers collect them. Adding a catalog type needs no change here unless it has a `string` argument that names something (add a case in `PlanValidator.string`) or must not be offered (`EXCLUDED`). A new supervisor action = `ACTIONS` + a case in `PlanValidator.action`, `Supervisor.apply`, the prompt list in `AiPrompts.superviseSystem`, `aiAct.<type>` in both catalogs and the panel's `actionEl`.
* **Queues.** Everything the AI queues has origin `ai:<plan id>` / `ai:<action id>`: not a planner origin, not soft — it behaves like a panel task (auto-supply plans materials, a planner assignment of that bot is released) and survives restarts in queues.json.
* **Supervisor state** (`Supervisor`): per project `State {seenAt, lastRunAt, inFlight, urgent, waiting}` (dropped when the project stops running; its pending suggestions expire), per bot stuck timestamps (10 min window), bot → last project (from assignments each tick, for `death` / `stuck` after the assignment is gone), the feed (`ArrayDeque`, 60 entries per project, memory only). `reassign` uses `planner.release` + `planner.roles().assign(bot, role, now)` — no config change.
* **Panel**: `js/ai.js` (`commandBox`, `dispatcherSection`, `connectionBox`); the bots screen, bot page, project page and settings → ai mount them; all stay hidden while `store.ai.enabled` is false.
