# Design decisions

Short records of where the code had to pick a behaviour SPEC.md leaves open. Format: `## <module>: <topic>`.

## common: schematic local origin
`Schematic` local (0,0,0) is the minimum corner of the whole schematic (for Litematica: of the union of all regions, negative region sizes resolved). This is the convention Baritone's own loaders use for the build origin, so `build`/`bom`/`progress` origins mean the same thing in the manager and the mod.
`Schematic.offset()` keeps the file's own origin (Litematica placement origin, WorldEdit copy origin: Sponge v3 `Offset`, v1/v2 `Metadata.WEOffset*`) for display only.

## common: transform order and pivot
`SchematicTransform` mirrors first, then rotates clockwise about local (0,0,0), then adds `origin` — exactly `StructureTemplate.transform` / Litematica. A rotated schematic therefore extends to the negative side of the origin; consumers must use `footprint()` (world box) instead of assuming `origin` is the min corner.
Block-state properties are not rotated in common (no Minecraft classes); the mod applies `state.mirror(m).rotate(r)` using `Mirror.name()` / `mcRotationName()`.

## common: canonical block-state strings
Both readers store states as `Ids.canonicalState`: namespace added, id lower-cased, properties sorted by name (`minecraft:oak_stairs[facing=north,half=bottom]`). Sponge files keep whatever order the writer used and Litematica has no string form, so sorting is the only way counts from different formats agree. Compare with MC state strings only after canonicalising both.

## common: overlapping Litematica regions
When regions overlap, a later region's air does not erase an earlier region's block (non-air wins). Litematica itself pastes regions one after another; for counting and BOM purposes losing blocks to an empty region is the worse error.

## common: legacy and vanilla structure files
`SchematicLoader` rejects MCEdit `.schematic` files (numeric ids) and vanilla `.nbt` structures with reason `unsupported`: numeric ids cannot be mapped to 26.2 states without game data. Sponge files named `.schematic` load fine because detection is by NBT content, not extension.

## common: BotConfig partial input
`BotConfig.parse(json)` merge-patches (RFC 7396) the input onto `BotConfig.defaults(botId, username)`, so a partial config or one from an older manager gets defaults for missing fields; a `null` member removes a default (e.g. a Baritone setting). Record constructors also replace null sections/collections with defaults/empty values, so plain `Json.fromJson(..., BotConfig.class)` never yields null sections, but missing scalars there are 0/false — use `parse`.

## common: glob matching details
`Ids.matches`: a glob without a namespace is in `minecraft:` (`*_pickaxe` does not match `othermod:steel_pickaxe`; use `*:*_pickaxe`), a lone `*` matches every namespace, and when the glob has no `[...]` the id's block-state suffix is ignored. SPEC §1 only says "matched against the full id after normalisation".

## mod: MVP scope
(Superseded by "mod: phase 2A scope".) Implemented task types: goto, goto_player, follow, explore, baritone, mine, farm, selection (op `clear` only), collect_drops, recover, eat, idle, take, deposit, inspect, equip. The other §3 types (craft, smelt_load, smelt_collect, breed, slaughter, shear, build, transfer, drop, guard, attack) and selection ops fill/walls/shell/replace finish with `unsupported`. Queries bom, progress and recipe_book answer `ok:false, error:"unsupported"`. `plugin` messages are dropped with a rate-limited `log` warning (companion bridge and protection guard are phase 2).

## mod: low-power activation
Before the first config, `ClientOpts.defaults()` apply only when the client was started by the manager (`baritonebots.link` set) or with `-Dbaritonebots.headless=true`; a hand-started client without either is not touched (SPEC "dormant except low-power" would otherwise cap a human's game at 10 fps). The three flags are independent: `lowPower` = forced options + loop cap (headless only), `skipRender` = render skip (headless only), `muteSounds` = sound engine cancel. 26.2 splits `GameRenderer` into `extract` and `render`; both are skipped with one per-frame decision. `SoundEngine#playDelayed` is cancelled too.

## mod: kicked vs disconnected
Both come from the `DisconnectedScreen` reason. A reason whose translation key starts with `disconnect.` or `connect.` (timeout, connection lost/refused, end of stream) is `disconnected`; anything else (literal text from plugins, bans, whitelist, server shutdown message) is `kicked`. A manager-requested `disconnect` emits `disconnected` with reason = the request text.

## mod: auto-login heuristics
Matching runs only between join and login success/failure. One command per 10 s, at most 4. If no success/failure line arrives within 10 s after sending, `login_ok` is sent with `data.assumed=true`; if no prompt arrives within 15 s after joining, the server is treated as auth-free (no event). `joinCommands` run once logged in, 1 s apart. Action-bar lines are checked for prompts but never forwarded; `chat` events are system lines only (≤10 per 10 s), whispers sent as signed player chat are not forwarded.

## mod: Baritone settings
`BotConfig.baritone` is applied with Baritone's own `SettingsUtil.parseAndApply` (JSON value rendered to Baritone's text syntax: numbers without trailing `.0`, arrays comma-joined, objects as `k->v`), which handles every setting type including block/item lists. Unknown or java-only names are skipped with a `log` warning. Settings set by a previous config but absent now are reset. `protection.noBreak` (when `protection.enabled`) is merged into `blocksToDisallowBreaking`.

## mod: task end
Every task end (success included) releases `task:*` pause claims, closes any open container, calls `cancelEverything()` and clears Baritone input overrides; keys are released unless auto-eat is mid-bite. Death fails the task with `died`, losing the server with `disconnected`. Tasks need to be in game and Baritone ready (else `disconnected` / `error`), except `idle`.

## mod: task details
* `goto` without `y` uses a horizontal-radius goal (`range`) or `GoalXZ` for range 0.
* `mine`: `data.collected` = every item gained during the task (ore drops differ from block ids); inactive with nothing gained = `not_found`. `minY`/`maxY` temporarily set `minYLevelWhileMining`/`maxYLevelWhileMining`.
* `selection clear`: builder paused = `stuck`.
* `take` adds `data.inventoryFull` when it stopped because the inventory was full; partial counts use right-click splitting.
* `deposit` keeps `keepCounts` items from the hotbar first, moves on when a container is full, adds `data.failed:[pos]`, and fails `container_failed` only if no container could be opened.
* `inspect` relies on the container sensor's snapshot; a container whose snapshot did not arrive within 20 ticks counts as failed.
* `equip` ranks armor and weapons by vanilla material tier from the id (wooden < leather < golden < stone < chainmail < copper < iron < turtle < diamond < netherite), then durability; unknown wearables (elytra, heads) are not replaced.
* `follow` sets `followRadius` = `radius` for the task and restores it after.

## mod: behaviours
* Defense moves with a temporary `DefenseProcess` (priority 900, below the pause process): `GoalRunAway(radius+8)` to flee, `GoalNear(target,1)` to close in, hold (pause) to melee within 3 blocks. It does nothing while eating or while a container menu is open. `retaliatePlayers` treats a player that hurt the bot (hurt animation running) as hostile. `threat`: once per entity type per 30 s.
* `damaged`: at most every 3 s; `tool_low`: main hand at or below `lowToolDurability`, once per item per 2 min; `food_low`: once per 2 min.
* Status `baritone.eta` is in seconds (`estimatedTicksToGoal / 20`).
* Container sensing only knows positions the mod itself right-clicked (`Interact.useOnBlock` → `ContainerSensor.noteUse`), within 100 ticks before the menu opened; no mixin on `useItemOn`.

## manager: MVP scope
(Projects, the planner and the companion bridge followed in phase 2C, see below.) Implemented: everything in SPEC §5/§6 except projects and the automatic planner (`/api/projects*` answered 501 `not_implemented`, the state snapshot has `projects: []`), Microsoft accounts (starting such a bot fails with 400 `unsupported`, `/api/bots/{id}/microsoft-login` answers 501 `unsupported`), the manager steps `sort_storage` and `smelt_all` (fail with `unsupported`), and the companion bridge (`plugin` messages from bots are dropped; `/api/bots/{id}/plugin` still forwards to the bot, which drops it too).

## manager: catalog flags and early rejection
`catalog.json` marks each task and manager step with `supported`; the task types the mod answers `unsupported` (since phase 2A: build, breed, slaughter, shear) are `false`. Queueing such a task over HTTP fails at once with 400 `unsupported` instead of reaching the bot. Arguments may carry `supportedEnum` (none does since phase 2A: every `selection.op` works); other values fail with `bad_args`/`unsupported`. Required arguments that have a catalog default (`selection.op`, `recover.dim`, `wait.sec`) are filled in by the manager, optional ones are left to the executor. Scenario steps are validated when the scenario is saved; unsupported ones fail when they are dispatched and stop the run.

## manager: runtime settings beyond SPEC §5.3
`runtime.mods[]` entries take either `url` (+ optional `sha512`) or `modrinth` (project slug) + `version` (preferred version number). Modrinth builds are looked up with `loaders=["fabric"]` and `game_versions=[minecraftVersion]`; when the preferred version is not listed the newest compatible build is used (logged), and Modrinth's sha512 is verified. Added `runtime.headlessmcSha256` (GitHub digest of 2.10.0, ignored for other versions) and `runtime.fabricInstallerUrl` (installer 1.1.2, written as `hmc.fabric.url`, because HeadlessMC's default installer is 1.0.3). `planner.depositKeep` (globs kept by `deposit_storage`) is new too.

## manager: runtime install
One install thread at a time; bots started meanwhile wait in state `installing`. `runtime/installed.json` records a core key (MC, loader, HeadlessMC version) and a mods key (enabled mods + bot mod sha256). A changed mods key re-downloads only what changed; the Fabric install + `-prepare` run again only when the core key changed, the Fabric version folder is missing, or the panel forces a reinstall. HeadlessMC runs in `runtime/setup/` with its own config.properties; output goes to `runtime/install.log`. Success requires exit code 0 and a `versions/*fabric*<mc>` folder.

## manager: bot launch details
Game JVM args in `hmc.jvmargs`: `-Xms min(256, Xmx)`, `-Xmx` from the bot / preset, G1 with `ParallelGCThreads=runtime.gcThreads`, `ConcGCThreads=1`, `G1PeriodicGCInterval=60000`, `UseCompactObjectHeaders`, `UseStringDeduplication`, `java.awt.headless=true`, the four `-Dbaritonebots.*` properties (link host is 127.0.0.1 when the link binds a wildcard), then `runtime.jvmArgs`, then the bot's `jvmArgs`. `hmc.gameargs=--quickPlayMultiplayer <address>` only when the server has `autoConnect`. `options.txt` is seeded only when absent (the game owns it afterwards); `baritone/settings.txt` is rewritten from the effective config on every start. Mods are copied into `game/mods/`; jars the manager put there earlier and no longer wants are removed (tracked in `mods/.baritonebots-managed`), other jars are left alone. `logs/launcher.log` rotates to `.1` at 5 MB at launch.

## manager: process lifecycle
Internal phases `stopped|installing|starting|running|stopping|crashed`; the panel's state adds `linked`/`online` derived from the link and the last status. A client that links without a manager-started process (started by hand, or still running after a manager restart) is accepted; stop sends `quit`, kill uses the `hello` pid. Priority (`below_normal`/`idle`) is applied to the launcher and every descendant process as they appear during the first 2 minutes (PowerShell `PriorityClass` on Windows, `renice` elsewhere). Restart policy counts crashes in a sliding 10-minute window; at `maxPer10Min` the bot stays crashed (event `crash_loop`). Starts are staggered globally by `startStaggerSec`, restarts included.

## manager: retries and death recovery
A task that fails with `died` or `disconnected`, or whose link drops while it runs, is re-queued at the head (at most 3 dispatches in total). On a `death` event the manager logs the death in the world document and, when `deathRecovery.enabled`, queues `recover {pos, dim, radius 6}` (timeout = `deathRecovery.timeoutSec`) at the front right away; nothing is dispatched while the bot is dead (death event, `died` result or `dead` status until `respawned` or an online status). Retried tasks are inserted after a pending recovery. `maxDistance` is checked when the recovery is dispatched (distance from the respawn point, same dimension only); too far = skipped with a warning.

## manager: inventory_full rule
For scenario steps: `deposit_storage` + the same step again, at most 50 times per run. For other tasks the same happens when `planner.autoDepositWhenFull` is on (50 per task chain). It needs at least one container with role `storage` in the bot's dimension; otherwise the failure is reported normally. `deposit_storage` deposits into all storage containers of the dimension in nearest-neighbour order, keeping `planner.depositKeep` plus the step's `keep`.

## manager: scenarios and queues
Cancelling a scenario step (or clearing the queue, or adding with mode `replace`) stops the run and removes its remaining entries. A failed step (other than the retried reasons) stops the run. Runs live in memory only: `queues.json` keeps queued entries (and the running bot task, re-queued first) across restarts but drops scenario entries. A cancel the bot never answers is dropped after 10 s.

## manager: kit planning details
Possessed items = status `items` (main + hotbar + offhand) plus worn armor. A slot is satisfied by any of its globs; one item counts for one slot only. Missing counts are taken from containers with role `kit`, then `storage` (same dimension, nearest first within a role), trying globs in rank order, exact ids from the snapshot. If any candidate container has never been seen, one `inspect` round runs first (the kit step is re-queued with `_inspected: true`, after which unknown containers are skipped). Takes are grouped per container and visited nearest-neighbour from the bot; `equip {armor: true, offhand: <first glob of a slot named "offhand">}` always follows. Shortfalls produce a `kit_missing` warning, not a failure.

## manager: world index
Every `container` snapshot updates the index; containers the index does not know are added without roles. `discover` adds `containers_nearby` results, giving furnaces/smokers role `furnace` and crafting tables `crafting`. `PUT /api/world/{id}` replaces the sections present in the body (validated on a copy first); changed zones are pushed to the server's bots as part of `protection.zones`.

## manager: HTTP extras
`GET /api/bots/{id}` exists; bot views include `password` (the AuthMe password from secrets.json, settable via `password` in POST/PUT `/api/bots`), `process`, `status`, `queue`, `client` (hello data) and the redacted `config`. JSON bodies are limited to 2 MiB, schematic uploads to 64 MiB, names to `[A-Za-z0-9][A-Za-z0-9 _.()+-]{0,95}` with a schematic extension; uploads must parse, and an existing name needs `?overwrite=true`. Validation errors are `{"error":"validation","fields":{path:code}}`. SSE also emits `world` (`{serverId}`) after world changes.

## manager: Windows AF_UNIX temp folder
Every NIO selector on Windows (JDK HttpServer, HttpClient) opens a loopback pipe through an AF_UNIX socket in the temp folder, whose real path must stay under ~100 characters; redirected temp folders (app containers) break it even when `%TEMP%` looks short. `ManagerMain` therefore sets `jdk.net.unixdomain.tmpdir` to `%USERPROFILE%\.baritonebots-tmp` unless it is already set.

## mod: phase 2A scope
(Superseded by "mod: phase 2B scope".) Added task types craft, smelt_load, smelt_collect, transfer, drop, attack, guard and the selection ops fill/walls/shell/replace; query `recipe_book`; the companion bridge (SPEC §7) and the protection guard. Still `unsupported`: build, breed, slaughter, shear and the queries bom/progress. Pure planning code (`mod.task.plan`) has JUnit tests in `bot-mod/src/test`.

## mod: craft
* Station: the 2×2 inventory grid when no `table` is given and a known recipe (or the `grid`) fits 2×2; else `table`; else the nearest loaded crafting table within 16 blocks (`not_found` when there is none). No recipe in the book and no `grid` = `not_found`; recipes the client's own material check (`RecipeDisplayEntry.canCraft`) rejects are skipped, and when nothing is left = `missing_materials` before walking anywhere.
* Exact counts: the recipe book is asked one set at a time (`useMaxItems=false` adds one set to an already placed recipe), "max" only while ≥ 64 crafts remain; the manual grid places exactly `n` per cell. A single `QUICK_MOVE` on the result then never overshoots by more than one craft's yield. Crafts are also capped by the room left for the result (a shift-click drops what does not fit), ending with `data.inventoryFull`.
* Fewer than `count` but at least one crafted = ok (`data.crafted` < `data.requested`); nothing crafted = `missing_materials`, `inventory_full`, or `bad_args` when the manual grid crafts nothing / something else. Data `{crafted, item, requested, inventoryFull?}`.
* Grid cells take ids or globs (`*_planks`), not item tags; a JSON string holding the grid is accepted as well. The pattern is moved to the top-left of the crafting grid.
* `recipe_book` entries add `count` (items per craft).

## mod: smelting
* `smelt_load` collects the result slot first, then loads input, then fuel. An input slot holding a different item fails with `container_failed` (run `smelt_collect all=true` first); a fuel slot holding a different item skips fuelling (`data.fuelBlocked`). No matching input in the inventory = `missing_materials`; input slot already full = ok with `loaded:0, inputFull:true`. Extra data `input`, `fuelItem`.
* `smelt_collect` shift-clicks up to 3 rounds; items left after that = `data.inventoryFull`.

## mod: transfer and drop
* `transfer` deposits only the item ids it took, keeping as many of each as the bot held before the task (`only` + `keepCounts`), so the bot's own stock is not moved. A failing take/deposit fails the transfer with that step's reason. Data merges take (`taken`, `missing`, `inventoryFull`) and deposit (`moved`, `left`, `failed`).
* `drop` uses main, hotbar and offhand, never worn armor; `count` -1 (or absent) = all. The bot looks level first so the items land a couple of blocks ahead, outside its pickup range. Data `{dropped, missing}`.

## mod: attack and guard
* `attack` measures `radius` from where the task started. Without `types` it targets `Enemy` mobs; with `types` any living non-player entity of those types (so animals can be named). Players are never targets. Done after 1 s without a target; data `{killed, unreachable, center}` (`killed` = fought targets seen dying). A target the path finder cannot reach (3 failed paths, or 10 arrivals still out of reach) is skipped.
* `guard` targets `Enemy` mobs inside `radius` of `center` only; unreachable ones are retried after 30 s. Outside the radius with nothing to fight it walks back to `GoalNear(center, min(4, radius/2))`; 5 failed returns = `path_failed`. It eats with the shared `Eater` only when auto-eat is off (food < 14, or health below half and food < 20).
* Both yield while the defense behaviour is engaged (it fights hostiles in its own radius, or flees in `flee` mode) or while eating.

## mod: selection ops
`block` is required for fill/walls/shell/replace and `from` (globs) for replace. `missing_materials` data counts block positions in loaded chunks that still differ from the target (replace: still match `from`) minus the inventory count of the block's item (key = block id when it has no item); boxes over 4 M blocks skip the count and report `stuck`.

## mod: protection guard
With `protection.enabled`, the `MultiPlayerGameMode` mixin refuses `startDestroyBlock`/`continueDestroyBlock` inside a zone of the current dimension (a zone without `dim` applies everywhere) or on a `noBreak` block, and aborts a break already in progress; refusals are logged (`log` warn, once per position per 10 s). Baritone only knows `noBreak` (merged into `blocksToDisallowBreaking`); a Baritone process aiming at a block inside a zone keeps retrying until the task times out.

## mod: companion bridge
`hello {token, botId, modVersion}` goes out every 2 s for 30 s after joining when `companion.enabled` (also when the setting is switched on while in game). Every plugin message, `welcome`/`reject` included, is forwarded to the manager as `plugin {payload}` (reliable send). `companion` events: `verified` (data = welcome payload + state), `rejected` (warn, data.reason), `absent` (info, after 30 s without an answer). Manager `plugin` messages while not on a server, without a `payload` object, or over 32 767 bytes are dropped with a `log` warning. Clientbound payloads over 1 MiB are ignored.

## mod: phase 2B scope
Added task types build, breed, slaughter, shear; queries bom and progress; `mine` options `strategy`/`y`/`fakeOres` (SPEC §5.7b3). Every SPEC §3 type is now registered. Pure code with JUnit tests: `mod.schematic.Placement` (checked against common's `SchematicTransform` for every rotation × mirror), `mod.schematic.BomRules` (fake block model), `mod.task.plan.AnimalFood`, `mod.task.plan.LegitMining`.

## mod: build
* The `box` mask is applied by cropping: Baritone gets a `PlacedSchematic` covering footprint ∩ box, built at the intersection's min corner. Baritone only looks at positions inside the schematic box, so for an axis-aligned box this is what `MaskSchematic` would do, without Baritone scanning the whole schematic every tick. A box that misses the footprint = `bad_args` (data.footprint).
* Coordinates: mirror first, then clockwise rotation about local (0,0,0), then `origin` (common's order and pivot); states `state.mirror(m).rotate(r)`. Baritone's own `RotatedSchematic`/`MirroredSchematic` rotate inside the bounding box (different pivot) and are not used.
* For the task the mod forces `schematicOrientationX/Y/Z=false`, `buildOnlySelection=false` and `startAtLayer=0` (any of them would shift or cut a sector), plus `buildInLayers` / `layerOrder` when given (`layerOrder` also accepts `"top_down"`/`"bottom_up"`); all restored afterwards.
* A missing / unreadable / unsupported file fails with `bad_args` (message names the file). ok data `{box, name}`; `missing_materials` / `stuck` data adds `box` and `todo` (loaded positions still to place). `data.missing` keys are item ids; blocks without an item appear under their block id.

## mod: bom and progress
* One half counts for two-block placements: the lower half of doors and tall plants (`half=lower`) and the foot of beds; the upper half / head is a position with no item. Double slab = 2; candles, sea pickles, turtle eggs, `flower_amount`, `segment_amount` and snow `layers` count their amount; candle cake = cake + candle; potted plant = flower pot + plant; plant bodies (`kelp_plant`, `cave_vines_plant`, …) and attached stems use the head's item / seeds. Skipped entirely: air, fluids (water, lava, any `LiquidBlock`), bubble columns, fire, portals, piston heads, moving pistons. Wall variants and crops go through `Block#asItem` (wall_torch → torch, wheat → wheat_seeds).
* `bom` data: `{items, blocks, unobtainable?}`; `blocks` = counted schematic positions in the mask (free halves and unobtainable blocks included).
* `progress` data: `{total, correct, missing, wrong, unloaded, toClear, remaining, unobtainable?, sectorBox?}`. Correct = same block and equal properties except volatile ones (waterlogged, power, open, age, distance/persistent, lit, …) and neighbour-derived ones (fence/pane/wall/redstone/tripwire/chorus/mushroom connections, stair and rail `shape`). Missing = world air, fluid or replaceable; wrong = anything else (or the same block in another state). `remaining` = items for missing + wrong positions + all unloaded positions (unknown state counts as still to build, so the planner can stock a sector before the bot gets there); a same-block mismatch adds only the difference (single slab where a double belongs = 1 slab, wrong facing = nothing). `toClear` = loaded positions where the schematic has air but the world has a block (Baritone clears them). `sectorBox` (footprint ∩ box) only when a box was given.
* Both answer through a job queue: the schematic is parsed on a loader thread (2 most recent files cached by path + size + mtime), then whole chunk columns are scanned within 15 ms per client tick. Errors: `bad_args: …`, `not_found: …`, `unsupported: …`, `not_in_game` (progress), `busy: …` (8 queued), `timeout` (120 s).

## mod: animals
* `breed`: the client never sees love mode or the breeding cooldown, so animals fed by any breed task are remembered by UUID for 5 minutes (static map); an animal that did not take the food within 10 ticks (cooldown, untamed, …) is remembered the same way. Eligible = adult, not remembered, reachable, and tamed for `AbstractHorse`/`TamableAnimal`. Pairs: nearest eligible animal, then the eligible animal nearest to it. A new pair starts only while population + pairs fed in the last 15 s < `max`. Default food from `AnimalFood`; other animals use the first inventory item `Animal#isFood` accepts (no animal in the pen and no default = `bad_args`); an explicit `food` the animal does not eat = `bad_args`. No food at start = `missing_materials`; running out after feeding = ok with `outOfFood`. The task waits 3 s after the last feeding so babies count. Data `{fed, population, untamed?, unreachable?, outOfFood?}`.
* `slaughter`: `keep` counts adults only — adults beyond `keep` are killed (nearest first), babies are never attacked and never count, so the breeding stock survives. Then every item inside the pen (+1 block) is collected. Data `{killed, picked, unreachable?}`.
* `shear`: only `minecraft:shears`; a sheep whose sheared flag does not flip after 3 tries is skipped. Wool (`*_wool`) inside the pen is collected afterwards. Data `{sheared, picked, outOfShears?, skipped?}`.
* "Inside the pen" = the entity's block position lies in `box`. During all three tasks fences, fence gates and walls are added to `blocksToDisallowBreaking`; Baritone may still open a fence gate to get in and does not close it.

## mod: legit mining and fake ores
* `strategy` is `normal` (default) or `legit`; `fakeOres=true` implies `legit`. Legit sets `legitMine=true` and `legitMineYLevel` = `y`, else the SPEC §5.7b3 level of the first requested ore (`LegitMining`), else unchanged. `fakeOres` also sets `legitMineIncludeDiagonals=false` (diagonal "magic" sight would target hidden, possibly fake ores).
* Baritone 1.19.0 has no position blacklist in its API (MineProcess keeps a private, obfuscated one). Its mine process re-reads the client world and drops targets that no longer match, so a fake ore that turned into stone is not mined again. The mod records such flips (`FakeOreWatcher`: target ores within 5 blocks are remembered; one that becomes another non-air, non-fluid block without being mined is fake) and, should the server send a recorded position as an ore again (re-obfuscated chunk), writes the real block back into the client world (client-only `setBlock`), which Baritone then ignores. No cancel/re-mine is needed.
* Results carry `data.strategy` (`legit`/`normal`) and, with `fakeOres`, `data.fakeOres` (positions blacklisted).
## manager: phase 2C scope
Implemented: game data from the client jar, projects (`/api/projects*`, `projects/<id>.json`, SSE `project`, events `project_*`), the planner (work items, matching, roles, locks, retries) and the `build` kind end to end, deficit resolution (haul / mine / craft / smelt / manual), the companion bridge on the manager side, server profile `antiXray`. Not yet: the other project kinds (gather, clear, farm, ranch, sort, smelt), autopilot, standing orders, schedules, rules, goals (`obtain`), Microsoft login, `sort_storage` / `smelt_all`; see the hooks in MANAGER-INTERNALS.md.

## manager: game data source
HeadlessMC's Fabric install keeps only `<mc>.json` in `versions/<mc>/`; the game jar sits in `versions/fabric-loader-<loader>-<mc>/fabric-loader-<loader>-<mc>.jar` (it carries the vanilla `data/`). Lookup order: `runtime.gameDataPath` (new setting: jar, zip or folder with `data/`), `versions/<mc>/<mc>.jar`, the Fabric folder, then any `versions/<dir>/<dir>.jar` named `<mc>` or `*-<mc>`; the first that yields recipes or loot tables wins. Parsed on a `gamedata-loader` thread (26.2 jar: 1491 recipes, 1113 block loot tables), published on the loop; a missing jar is looked for again on every planner tick, a failed parse waits for a settings change. Recipes: shaped, shapeless, smelting, blasting, smoking, campfire, stonecutting; ingredients as id, `#tag`, list or legacy `{item|tag}` objects; recipes with an unknown or empty tag and special types are skipped. Loot ("drops without silk touch"): pools and entries guarded by a non-inverted `match_tool` (also inside `any_of`) are skipped; `alternatives` stop at the first child that always applies; `random_chance*` / `table_bonus` mark drops as not guaranteed; `tag` entries expand; `dynamic` and nested tables are ignored. `toolFor`: kind from `mineable/<kind>` (pickaxe, axe, shovel, hoe in that order), tier from `needs_{diamond,iron,stone}_tool` (else wood); `required` = pickaxe blocks or any `needs_*` tag (an approximation of the per-block flag in game code).

## manager: planner model
`Planner` ticks every `planner.tickSec` on the loop (plus a debounced tick 300 ms after an assignment ends). Work comes from `WorkSource`s (running projects); items carry a stable id, so retries survive ticks. Idle = enabled, online, alive, nothing current or queued, no assignment. Matching is global and greedy (score desc, then bot id, item key). The role cooldown is strict: inside `roleSwitchCooldownSec` a bot only takes items of its current role (a bot without a role takes anything; the timer restarts only on a real change; in memory only). An assignment pushes batches of queue entries with origin `project:<id>`; when no entry of that origin is left on the bot the source gets the batch results. Manual work wins: queueing any entry whose origin is not `project:*` or `recovery` releases the assignment, removes its queued entries and cancels its running one. A planner task cancelled from the panel releases the assignment and rests the bot for 60 s. A bot offline or dead for 60 s loses its assignment. Failures: backoff 30 s × 2^(n−1) (max 10 min); the 3rd failure marks the item failed (event `project_blocked`) until the project is started or resumed again. `queues.json` drops `project:*` entries on load (assignments are not persisted; running projects re-plan).

## manager: build projects
Config `{schematic, origin, dim, rotation, mirror, supply?:[pos]}` (also accepted as top-level `placement`); the file must exist in `schematics/`. The manager loads the schematic itself (worker thread) for the footprint and, per item and split-axis column, the lowest Y ("bottom layers first": restock needs are sorted by the lowest Y of the item inside the sector; block ids map to items for wall variants, crops, wires, pots). BOM: one `bom` query, cached in the project file under `fileHash|origin|rotation|mirror`; 3 failures → blocked, `bad_args`/`unsupported` → project failed. Sectors: `Box.split(builders, 4)` where builders = allowed, enabled, online bots that may be builders (min 1); a different count must hold for 30 s before a re-split; finished sectors never move, adjacent unfinished ones are merged and cut again (≥ 1 per run, proportional widths); builders on a sector that no longer exists are cancelled and matched again. Never-checked sectors are surveyed with one `progress` query at a time through any project bot; the project-wide remaining estimate is the sum of sector `remaining` once every sector has data (the BOM before that). Builder loop: `progress` (sector) → done when missing, wrong and toClear are 0 and nothing is unloaded; when only unloaded positions are left the bot walks the sector in ≤ 32-block pieces (`goto` + `progress` per piece) and accepts it if nothing is missing; otherwise needs = remaining − inventory, `take` from supply, then storage, then fuel containers (unknown contents → one `inspect`), within `freeSlots − restockFreeSlotsTarget` slots; a full inventory with nothing useful runs `deposit_storage` once; then `build {file, origin, rotation, mirror, box}` (timeout 30 min; a timeout just re-checks); `missing_materials` → re-check and restock (after 4 rounds, or when nothing can be taken, the sector waits 15 s doubling to 2 min; supply growth clears all waits). When every sector is done a final pass marks all sectors `verify`; each is checked again the same way (and rebuilt if needed); all verified → `done`. `maxBuildersPerSector` is the sector lock capacity. Stack sizes and fuel values are id heuristics (`ItemStacks`).

## manager: deficit resolution
Deficit = remaining − supply − builders' inventories − in transit (items promised by running haul/mine/craft/smelt assignments). Storage stock (minus other assignments' reservations) becomes `haul` work when the project has supply containers (without any, builders take from storage directly). Mining candidates: blocks whose loot drops the item, minus the item's own block when it is craftable (planks, bricks), minus chance-only drops of craftable or smeltable items (sticks from leaves), minus farmland, paths and infested blocks; when a `base_stone_*` block drops the item, the item's own block is skipped (cobblestone comes from stone). Crafting uses the first crafting recipe whose ingredients are obtainable (3×3 only with a known crafting table: role `crafting` or any indexed `crafting_table`); ingredient options pick the one in stock, else the easiest (mine < craft < smelt). Ingredients may use storage and supply beyond what the build still needs. Smelting needs a role `furnace` container whose block runs the recipe type (furnace / blast furnace / smoker; campfire and stonecutting recipes are never used); fuel = the best fuel in stock, else coal (recursing). Recursion depth 8 with a cycle guard; the rest is `manual` (event `project_blocked` per item, at most every 10 minutes). Only actions whose inputs are in stock become work items; the others show as waiting in `production`. A mine item whose tool (`toolFor` of the first block) no bot or container has is not offered (blocked note). Smelting waits next to the furnace (`wait` count × 10 s, 5 s for blast furnace and smoker) and collects; at most 64 items per assignment. Results are deposited into supply (storage when there is none) with `only` = the item; without any supply or storage container no production work is offered.

## manager: anti-xray
Server profile `antiXray: none|hide|fake` (new setting, default none). Planner `mine` items get `strategy: "legit"` (+ `fakeOres: true` for fake) only when a target block is an ore (`*_ore`, ancient debris): anti-xray only hides ores, and legit mode would slow down stone or log mining for nothing.

## manager: projects API
Body `{id?, name, kind, serverId, bots: "any"|[botId], priority? (0–100, default 5), config, start?}`; ids follow the config id pattern (generated `p-…` otherwise). `start` works from draft, failed and done (a finished build re-verifies every sector), `pause` from running, `resume` from paused, `stop` from running or paused and returns to `draft` (message `stopped`, progress kept). PUT may change name, bots and priority at any time; config or server only when not running or paused (409 `bad_status`), which also resets the kind state. The view adds `progress {total, placed, remaining, percent, blocksPerMin, etaSec, missing, wrong, unloaded, sectors, sectorsDone, finalPass}`, `footprint`, `sectors [{index, state pending|active|done|blocked, verify, verified, box, placed, total, botId, waitingMaterialsUntil}]`, `manual [{item, count}]`, `blocked [{key, reason}]`, `assignments [{botId, role, workItem, since, phase}]`; GET by id adds `bom` rows `{item, needed, remaining, inSupply, inBots, inTransit, deficit, source}`, `production` and `gameData`. SSE `project` carries `{project: view}` (every planner tick while running) or `{id, deleted: true}`. Project events carry `data.projectId`; `GET /api/events?project=<id>` filters on it.

## manager: companion bridge
`plugin {payload}` from a bot: the payload (the plugin's envelope) is kept per type on the bot (last 16 types, with `receivedAt`; bot view field `plugin`, also `GET /api/bots/{id}/plugin`); `notice`, `rollback_result` and `journal_result` become events `plugin_notice` / `plugin_rollback` / `plugin_journal` with source `plugin`. `welcome` and `reject` are only stored (the mod already reports `companion` events). `POST /api/bots/{id}/plugin {payload}` sends `plugin {payload}` to the bot.

## manager: HTTP extras (phase 2C)
`GET /api/planner` (tick, sources, assignments), `GET /api/gamedata` (load state, source, counts), `GET /api/gamedata/item/{id}` (recipes, smelting, drops, blocks dropping it, tool; 409 `not_loaded` without data), `GET /api/bots/{id}/plugin`; `/api/state` also has `gameData`; `catalog.json` has `projectKinds` (the panel's create form; only `build` for now).

## manager: autopilot through the planner
Sorting, idle work, inspections and refills are `AutopilotSource` work items (one source per server profile, origin `auto:<server>`); standing orders are `OrdersSource` items (origin `order:<server>`). `Planner.isPlannerOrigin` now covers `project:`, `auto:` and `order:`, so a manual or scenario entry still cancels them. Autopilot items are role-neutral (`role == null`: allowed for every bot, no role change, no cooldown, `RoleTracker` untouched — idle work must never lock a builder out of building for `roleSwitchCooldownSec`) and have negative priorities (refill 5, sort −1, collect −1.5, refuel −2, inspect −2.5, home −5), so project and order items (≥ 0.5) win. Only auto-supply bypasses the planner: it has to run in front of whatever task comes next.

## manager: auto-supply step
Implemented as an internal manager step `supply` that the dispatcher pushes in front of a task (once per entry id), not as takes computed synchronously at dispatch: the step reads the live inventory (query; status fallback) for durability and exact counts, can inspect unknown containers and plan again, and for a manual `build` asks the bot for the `progress` remaining items. Its takes use origin `supply` so a failed take never stops a scenario, never ends up in a planner batch decision and never counts as manual work; the step itself carries the task's origin (scenario runs and planner batches see it). Projects already restock their own materials, so planner-origin tasks only get tools, food and blocks. Tools that the block does not strictly need (axe for logs, hoe for farms, pickaxe/shovel/axe for clearing, swords) are optional: fetched when present, never reported. Food refills to 2 × `foodMin`, blocks to 2 × `blocksMin`, so not every task triggers a trip.

## manager: discovery defaults
Containers found by `containers_nearby` get roles by block: furnaces → `furnace`, crafting tables → `crafting`, chests/barrels/shulker boxes → `storage` within `autopilot.homeRadius` (24) of a `home` waypoint (or any bot's home waypoint), else the new role `found`; trapped chests, hoppers, droppers and dispensers stay role-less. `found` containers are a source only with `autopilot.useFound` (default false: on a shared server they are other players' chests). The HTTP `discover` endpoint uses the same rules. Containers are never removed automatically (a vanished chest only fails its inspection and is skipped for an hour). Scans run only from bots that are not mining/building/exploring/farming, at most every `discoveryIntervalSec` and only after moving half the radius (or every 10 min).

## manager: sorting rules
Categories match in configuration order (first match wins; `#tag` entries need game data), so the broad `stone_building` globs (`*_slab`, `*_stairs`) come after `wood`; anything else is `misc`. Adoption = more than half of the occupied slots (stack-slot units). Targets per category: its `sorted:<cat>` chests with room (free slots + top-ups of partial stacks from the snapshot), then empty unassigned storage chests (one claimed per category per round; the next adoption pass tags it), then `sorted:misc`; mixed unassigned chests are never targets. Without any inbox, `deposit_storage` deposits each category into its chests first (when sorting is on) and then everything else into inbox/storage as before.

## manager: standing orders storage
Orders live in `config.json` → `orders[]` (schema-validated: unique id, known server, item id pattern, max ≥ min, `into` = role / `sorted:<cat>` / container id) so the settings page edits them without new panel code; `/api/orders` adds CRUD over the same list plus live status. Stock counts only the `into` containers' snapshots (minus other assignments' reservations); in transit = `promised` of the order's running assignments. Order sources exclude project `supply` chests.

## manager: goals
`obtain` simulates the whole recipe tree every round against the live inventory and runs the first ready action, instead of keeping a static plan: whatever happened (a mine collected spruce instead of oak, a take found less than the snapshot said) is corrected on the next round. Logs are mined as "any log" and the cost estimate then picks the planks the bot can actually make. A crafting table / furnace is placed with a one-block `selection fill` — the mod has no place task, Baritone commands cannot place a given block, and the builder path is the one already live-tested — at a spot chosen with `block_at` queries (air-like with a solid block below; first candidate as fallback, the builder clears it). Furnaces count within 48 blocks (tables 16, per SPEC). There is no wooden or stone armor: `progress wood|stone` asks for leather armor as a soft goal; torches and food are soft for every tier (coal or food may simply not exist nearby); tools and iron/diamond armor are required. `obtain @food` takes food from storage, else cooks raw food the bot carries.

## manager: stuck detection
Progress = position moved ≥ 1 block, or the status' task step / progress, or Baritone's goal changed; ETA changes are ignored (a stuck pathfinder keeps recalculating). Paused tasks (eating, fighting) restart the window; `guard`, `follow`, `idle`, `eat` are exempt. The step back is a 30 s `goto` 3 blocks opposite the bot's yaw with origin `recovery` (its failure never stops a scenario); the retried entry is reported to the planner as re-queued, so the assignment survives.

## manager: goal cost model
Choices inside `ObtainPlanner` (which recipe, which ingredient option, coal vs charcoal, which log for fuel) use a per-item effort estimate that follows the same precedence as the planner itself (craft → smelt → mine; otherwise a stray guaranteed drop such as sticks from dead bushes makes items look cheap): crafting = 1 + Σ(ingredient effort × count) ÷ yield (2 planks → 4 sticks beats 2 bamboo → 1 stick), smelting = 2 + input, mining = 3; a missing tool / table / furnace adds a quarter of its own effort; at hand 0, in storage 1. Costs only look at the inventory and storage before planning (the simulation pool changes while planning), so the memo stays valid; equal costs stay with options the plan already chose. Checked against the real 26.2 client jar: wooden/stone/iron/diamond pickaxe, 32 torches, iron chestplate, furnace, glass and chest from an empty inventory all complete in ≤ 16 rounds (< 20 ms per round) with one log trip and coal (not charcoal) for torches; bread is correctly "manual" (wheat needs farming).

## manager: non-build project kinds
`gather`, `clear`, `farm`, `ranch`, `sort`, `smelt` share `KindRuntime` (work-source basics, container resolution, deposits, inspections, blocked notes, `percent`) instead of a bigger framework; each kind is one file with its `ProjectKind` and a nested runtime, pure planning parts are static and unit-tested. Choices: `gather` counts a delta of the indexed stock in its targets (baseline at start; items taken out by players lower the progress), its sources exclude the targets; a `box` **or** a named `area` (resolved to its box and dimension when the project is saved, the name kept for display) for clear / farm / ranch; `clear` slabs are fixed at the first tick (one per allowed bot with role miner or none, never re-split; extra bots take free slabs), the dispatcher's existing `inventory_full` → `deposit_storage` + retry handles full inventories, and verification samples 5 `block_at` positions per slab (air, fluids, bubble columns and light blocks count as cleared because Baritone's clear does not drain fluids); `farm` uses the bot's `farm` task as is (Baritone replants), capacity `farmers` (default 1) on one item; `ranch` slaughters only when the breed result reports a population ≥ `max` (a full pen), so the herd oscillates between `keep` and `max`; `sort` reuses the autopilot sorter through new public `Autopilot.sortPlan` / `sortMoves` / `adoptCategories`; `smelt` and `smelt_all` share `Smelter.plan` with the autopilot's refuel (the input with most stock, best known fuel; `fuel` globs allow any burnable item; a load never needs more than 64 fuel items). `smelt` re-arms a furnace after `smelt_collect` when the closing snapshot still shows input, because nobody else re-opens it.

## manager: schedules and rules
Stored in `config.json` (`schedules[]`, `rules[]`, schema type `json` for the nested parts so the settings page edits them without new panel code) with CRUD routes like orders. Cron is a small own parser (5 fields, Vixie semantics) — no dependency. `BotStatus` has no world time, so `day` / `night` use the new server profile fields `dayStart` / `nightStart` (local HH:MM, defaults 07:00 / 22:00); `DayNight.isNight` already takes a world day time for when the mod reports one (needs a `BotStatus` field, e.g. `dayTime` = `Level#getDayTime`), and they fire only on a transition. Rule and schedule steps are user intent, so they are not planner origins (auto-supply plans materials for them, they persist in queues.json), but they are "soft" (`Planner.isSoftOrigin`): `priority:"normal"` (default) appends them and the bot runs them when its current planner batch ends — project work is not cancelled, which keeps e.g. a 30-minute sort schedule from tearing builders off their sectors; `priority:"high"` releases the planner assignment and queues at the front (a running manual task still finishes). A bot that still has entries of the same schedule/rule is skipped to avoid pile-ups. `botIds`: `any` (one free online bot), `all` (every online bot) or a list (each listed bot, queued even while offline); steps of bot events and `healthBelow` run on the triggering bot. State triggers fire on rising edges with an armed retry after the cooldown; `playerOnline` = seen by a bot's `player` query (tracking range) or announced by a join chat line, because the mod exposes no tab list. Events emitted by rules and schedules never trigger rules.

## manager: Microsoft login
Implemented with HeadlessMC 2.10.0's own device-code flow, verified against the jar: `--command login` prints `Go to https://www.microsoft.com/link?otc=<code>` and keeps the process alive (its login thread is an exit-manager task) until the code is confirmed, then prints `Logged into account <name> successfully!` and saves the account to `HeadlessMC/auth/.accounts.json` (`hmc.store.accounts` defaults to true). Running it with `bots/<id>` as working directory gives every bot its own account store; no stdin interaction is needed. The code is parsed from the `otc` parameter (HeadlessMC prints only the direct URL). A Microsoft bot launches with `hmc.offline=false` and without `-offline`; HeadlessMC refreshes the token on each game launch (`hmc.account.refresh.on.game.launch` default true). Without a stored account `start` answers 409 `login_required`. The child JVM gets `Os.childJvmFlags()` (the AF_UNIX tmpdir fix), without which HeadlessMC fails with "Unable to establish loopback connection" on Windows. Not verified end to end with a real account (no login was completed); the bot's configured `username` should match the Microsoft profile name (`microsoft_login_ok` warns when it does not).


## common: BotStatus.dayTime
Optional `Long dayTime` (last record component, null when not in game or from an older mod; Gson leaves it null when absent). 26.x replaced `Level#getDayTime` with world clocks, so the mod sends `ClientLevel#getOverworldClockTime()` folded to 0..23999 — the overworld clock also while the bot is in the Nether or the End, because schedules mean the server's day. `ScheduleService` takes it from the freshest status of an online bot of that server profile and falls back to `dayStart` / `nightStart` (supersedes the "no world time" note in "manager: schedules and rules").

## plugin: companion plugin
Main class `BaritoneBotsPlugin` wires the existing parts; `CompanionProtocol` answers the channel, `BotListener` holds the events, `AdminCommand` the command, `rollback.RollbackService` owns the one running `RollbackJob` (it is package-private there). Choices: `welcome.features` lists only what the current config can deliver (not the fixed SPEC list); replies carry `re` when the request had an `id`, and extra fields (`error` code, `target`, `minutes`, `total`/`skipped`/`failed`, `command`, `pluginVersion`) that the mod and manager pass through; `reject` carries a human `reason` in the plugin language plus a machine `code`; `rollback_result.restored` is 0 in command mode (unknown). An unverified connection gets one `not_verified` answer, then silence. `/bb reload` with a changed token, or with a bot removed from `bots`, revokes the verification (`reject`, perks removed). `BlockMultiPlaceEvent` has no handler list of its own, so it is handled inside the `BlockPlaceEvent` handler via `instanceof` (a second handler would see every multi-place twice). Breaks record `minecraft:water` as the after-state of a waterlogged block. Logs stay English; chat and bot-facing texts come from `lang/en|ru.properties`.

## common: owner and labels in the protocol
`BotConfig.owner {player, prefix, patterns}` (new last record component, defaults in `BotConfig.Owner.defaults()` so the manager schema and the mod cannot drift) and `ContainerSnapshot.signText` / `frameItem` (new last components; the old 8-argument constructor stays for callers without labels). Gson leaves them at their defaults / null when absent, so an older counterpart only loses the feature.

## mod: owner commands
Signed and unsigned player chat carries its sender (`GameProfile`), so no pattern is needed there and nobody can spoof the owner through it; whispers arrive the same way (chat type `msg_command_incoming`). Only system lines (chat plugins, Essentials messages) need `owner.patterns`; the first matching pattern decides who spoke, so a looser later pattern cannot re-read `<Mallory> Owner: !b stop` as the owner's line, and every default pattern is anchored at the line start. System lines are only as trustworthy as the server's chat format (a nickname plugin that lets players display as the owner can spoof them); this is documented, not prevented. Rate limit 5/s; rate-limited owner lines are swallowed, never forwarded as `chat`. Look direction = `calculateViewVector(xRot, yHeadRot)` of the tracked player: the server syncs head yaw and pitch for players, and the lerped values are what the owner sees. The bot's own render distance limits the ray (64 blocks, unloaded chunks count as air).

## mod: scan_blocks and heightmap
`scan_blocks` resolves ids / block tags to a `Block` set once (iterating the block registry; tags are synced to clients), then walks chunk sections in the slow-query queue (shared 15 ms budget, one section between deadline checks) and skips sections by palette (`maybeHas`). Clustering is cell-based instead of per block: cubes of `gap` blocks keep count, bounds and per-id counts, connected cells (26-neighbourhood) form a cluster. That bounds memory by cells (50 000 max, `truncated`), makes the build incremental with the same deadline, and gives a precise rule (blocks closer than `gap` join, `2·gap` apart never link directly); gap 2 bridges the water lines of farms, gap 1 is exact connectivity for fences. `heightmap` answers in one go (≤ 193² columns, chunk cached per run of 16) and steps down through replaceable plants / snow layers so grass does not count as a bump; liquids and trees are flagged instead of hidden so the manager decides.

## mod: drop and deposit by slot
The trash step must throw the worn-out duplicate, not just "one iron pickaxe", so `drop` and `deposit` accept `slots:[{slot, item, count}]` from an `inventory` answer. Counts are relative to the stack size at task start and a slot whose item changed is skipped, so items picked up or eaten in between never make the task take the wrong stack.

## manager: position references
References are resolved at dispatch time for bot tasks through an internal `resolve` manager step (same id for the resolved task, so scenarios, planner batches and retries keep tracking it; the bot never sees a reference), and at save time for projects and world edits — a project or waypoint has to show real coordinates in the panel and a running project must not move when the owner walks away. Unresolvable references fail the task (reason `ref_*`, event `ref_failed`) or the request (400 with the reason as error code). The owner is found by asking every online bot of the server (first `found` wins, 1.5 s cache); `owner_command` events carry the same data, so commands need no query. `auto` is kind-specific (`AutoDetect`): farm fields, pens and build sites through `scan_blocks` / `entities` / `heightmap` of the online bot nearest to home (≤ 128 blocks: a client only knows the chunks around itself — detection works best while a bot idles at home, which the autopilot does), plus container lists from the index; arguments without a rule fail with "not available". `goto` gained a `pos` argument (x / z became optional, checked together in `TaskCatalog.normalize`) instead of a reference per coordinate. The panel pickers are not part of this change: the catalog marks the arguments (`refs: true`, `/api/catalog → refs`) and both catalogs carry the `ref.*` labels.

## manager: owner commands
Every bot on the server hears a public command, so commands are de-duplicated per server and text (2.5 s). Whispered commands address the bot they were whispered to; public `come` / `follow` / `stop` / `trash` address all online bots (that is what "bots, come here" means), `progress` / `obtain` the best free bot (`StepRunner.pick`), `@name` / `@all` / `@any` override. `come` / `follow` replace the bot's queue (the owner wants them now; a FRONT entry would wait for the running task), `stop` clears it (a cancelled planner task rests the bot 60 s, so it stays put for a while). Work has origin `owner`: manual, it wins over project work and survives restarts. `build` creates and starts a project with `bots:"any"` (materials, sectors and verification come with it) at the looked-at block + 1 (looking at the ground means "build on it"), rotation from the yaw so the schematic extends away from the owner and to their left (the schematic's +z axis points where the owner looks). `farm` / `ranch` start the server's existing project of that kind, else create one at the automatically found field / pen. Russian aliases are accepted for every verb. Replies are whispers from the bot that heard the command (`general.ownerReplyCommand`, default `/msg {player} {text}` — Essentials overrides `/msg` compatibly), one per second per server; RU texts use «вы».

## manager: sign labels and role precedence
Containers record `roleSource` (`manual | sign | auto`). Roles changed through `PUT /api/world` (compared per container id) or the `chest` owner command are manual; sign roles replace automatic ones but never manual ones; category adoption skips sign containers (a «склад» sign means general storage). Entries saved before this change have no source: they count as manual when they carry a role the autopilot never assigns (inbox, kit, supply, fuel, trash), so an upgrade does not let a nearby sign overwrite them. A disappearing label returns the container to its automatic default roles. Dictionary matching is word-based with prefix matching from 4 letters (Russian word forms: склад → склада, инструмент → инструменты) and exact matching for short words (кит ≠ китайский); the defaults include a few extra forms (руды, еды, приём / прием) and roles beyond the SPEC list (supply, fuel, trash). `ConfigStore.normalize` now takes dotted MAP / JSON fields as given (like top-level ones), so deleting a default sign word or keep count sticks.

## manager: keep profiles and trash
The default profile «снаряжение» follows SPEC (worn armor, best sword, best pickaxe and axe, 64 food, 64 throwaway blocks) plus `extra` torches, shield and water bucket, which a working bot should not throw away. Best-of-kind = tier (`ProductionWork.toolTier`, golden = wood), then durability, then slot; a tool kept by `extra` / valuables counts as the best of its kind. Armor in the inventory stays only when it beats the worn piece of its slot. For `drop` and `trash_chest` valuables (shulker boxes, named items, diamonds, emeralds, netherite, elytra, totems, tridents, maces, …) are never surplus — "throw away junk" must not destroy loot; `store` hands everything over. Auto-trash decides on the last status (no extra query at failure time): at least two junk stacks (one without any storage), else the usual deposit + retry; `explore` is included with `mine` / `selection` because it fills the inventory the same way. Thrown junk lands a few blocks ahead (the drop task looks straight ahead first) and the 2 s pickup delay usually lets the bot move on; Baritone only chases drops of its mining targets, so junk is rarely picked up again.

## manager: optional local AI
SPEC §5.7c/d leave the transport and the shapes open; chosen: the plan format carries standing orders (`orders[]`) beside steps and the project draft, because "keep N in stock" is one of the high-level answers the prompt asks for. All `any` steps of one plan go to the same free bot in order ("собери 64 железа и сложи в склад" = obtain + deposit on one bot). Raw `baritone` commands and `recover` are never offered or accepted: their text cannot be checked against the catalog. Literal coordinates pass only when every number is in the owner's text; the supervisor has no text, so it can only use references. A plan is checked twice (when parsed and again on run, against the live state) and runs once. `reassign` is the planner's role hysteresis (release the assignment + `RoleTracker.assign`), not a config edit, so it wears off after `roleSwitchCooldownSec`.
